1. Executive Summary

This document describes an enterprise-grade Food Delivery Microservices Backend similar in concept to platforms like Zomato or Swiggy. The system is built as a Maven multi-module monorepo containing eleven deployable Spring Boot applications plus a shared library.

Key design principles implemented in this project:

  • Microservices architecture — each bounded context owns its database and deployment lifecycle.
  • Layered architecture — consistent controller → service → repository pattern in every service.
  • DTO-only APIs — JPA entities are never exposed over HTTP or Feign.
  • Service discovery — Netflix Eureka registers all services dynamically.
  • Centralized configuration — Spring Cloud Config Server with native file repository.
  • API Gateway — single entry point with path-based routing and load balancing.
  • JWT + RBAC — stateless authentication with role-based access in auth-service.

3. System Architecture

3.1 High-Level Architecture

External clients (mobile apps, web frontends, Postman) communicate only with the API Gateway. The gateway resolves service instances via Eureka and forwards requests. Business services do not call each other directly except where orchestration is required — the Order Service coordinates customer validation, payment, notifications, and delivery assignment via OpenFeign.

4. Microservices Overview

4.1 Infrastructure Services

Discovery Server (Eureka)

All microservices register on startup. The API Gateway uses lb://service-name URIs to route to healthy instances. Eureka dashboard: http://localhost:8761.

Config Server

Reads configuration from config-repo/ (native profile). Each service imports config via spring.config.import=optional:configserver:http://localhost:8888. Shared settings (JWT secret, Eureka URL, JPA) live in application.yml; service-specific ports and DB URLs in {service-name}.yml.

API Gateway

Spring Cloud Gateway routes external paths to internal services. Example: /api/customers/** → lb://customer-service with StripPrefix=1 so /api/customers/1 becomes /customers/1 on the downstream service.

5. Layered Architecture Pattern

Every business microservice follows the same package structure and layering:

controller — REST endpoints, ResponseEntity, validation
▼
service (interface) + serviceImpl — business logic
▼
repository — Spring Data JPA
▼
entity — JPA @Entity (never exposed in API)

Horizontal packages: dto (RequestDto / ResponseDto), mapper, config, security, exception (local if needed).

Rule: Controllers accept and return DTOs only. Mappers convert Entity ↔ DTO inside the service layer. Feign clients use separate client DTOs in order-service (never entities).

7. Security & Authentication

7.1 Roles (RBAC)

RoleTypical Use
ADMINPlatform administration
CUSTOMERPlace orders, view profile (referenceId = customerId)
RESTAURANT_OWNERManage restaurants and menus
DELIVERY_PARTNERDelivery status updates

7.2 JWT Flow

  1. User registers via POST /auth/register with email, password, role, referenceId.
  2. Password stored with BCryptPasswordEncoder (constructor-injected).
  3. Login via POST /auth/login returns JWT with claims: role, userId, referenceId.
  4. Subsequent requests send Authorization: Bearer <token>.
  5. JwtAuthenticationFilter validates token and sets SecurityContext.

10. Business Flows (End-to-End)

10.1 Customer Registration & Login

1. POST /api/customers → Create customer (id=1) 2. POST /api/auth/register → role=CUSTOMER, referenceId=1 3. POST /api/auth/login → Receive JWT token 4. Use Authorization: Bearer <token> on protected calls

10.2 Restaurant & Menu Management

1. Register RESTAURANT_OWNER in auth-service 2. POST /api/restaurants → Create restaurant 3. POST /api/menus → Add items (restaurantId, price, availability) 4. PUT /api/menus/{id} → Update menu / toggle availability

10.3 Order Placement (Orchestration)

POST /api/orders │ ├─► Feign: CustomerClient.getCustomer(customerId) [validate] ├─► Feign: RestaurantClient.getRestaurant(restaurantId) [validate] ├─► Save Order (status=PLACED) ├─► Feign: PaymentClient.processPayment(...) ├─► Update Order (status=CONFIRMED) ├─► Feign: Notification "ORDER_PLACED" └─► Feign: Notification "ORDER_ACCEPTED"

10.4 Delivery Assignment

POST /api/orders/{id}/assign-delivery │ ├─► Feign: DeliveryPartnerClient.assignPartner(orderId) │ └─► Picks first available partner, status=ASSIGNED └─► Order status → OUT_FOR_DELIVERY PATCH /api/delivery-partners/{id}/status └─► ASSIGNED → PICKED_UP → OUT_FOR_DELIVERY → DELIVERED (on DELIVERED: partner becomes available again)

10.5 Payment (Simulated)

Payment service creates record with PENDING, immediately sets SUCCESS. Suitable for demos and learning — replace with payment gateway integration in production.

14. Learning Guide

Recommended Study Path

  1. common-lib — Understand shared exceptions and enums first.
  2. customer-service — Simplest CRUD; study layered packages.
  3. auth-service — JWT, SecurityConfig, filter chain.
  4. discovery-server + config-server + api-gateway — Infrastructure wiring.
  5. order-service — Feign clients and orchestration in OrderServiceImpl.
  6. delivery-partner-service — State machine for delivery status.

Concepts Demonstrated

  • Database-per-service pattern
  • API Gateway as BFF / edge router
  • Synchronous orchestration vs eventual saga (extension topic)
  • DTO boundary between services
  • Centralized configuration without redeploying all JARs
  • Constructor injection and testability

Production Enhancements (Future Work)

  • Propagate JWT through Feign (RequestInterceptor)
  • Resilience4j circuit breakers on Feign calls
  • Kafka for async notifications
  • Distributed tracing (Micrometer + Zipkin)
  • Kubernetes manifests and CI/CD pipelines
